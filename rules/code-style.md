# Код-стайл

Общие правила, не зависящие от языка. Конкретные имена пакетов, базовых классов, исключений и
утилит проекта перечисляй в `CLAUDE.md` проекта — правила ниже ссылаются на них по роли.

## Архитектура

- Соблюдай слоистую архитектуру: точка входа (endpoint / controller / handler) -> сервис (бизнес-логика) -> репозиторий (доступ к данным). Слой не обращается к слоям выше себя и не перепрыгивает через соседний.
- Раскладывай код по ролям: точки входа, бизнес-логика, модели запросов, модели ответов, сущности хранилища, доступ к данным — каждая роль в своём пакете / модуле / директории по принятой в проекте схеме.
- Если в проекте есть автоматические архитектурные проверки (ArchUnit, import-linter, dependency-cruiser, deptrac и т.п.) — учитывай их при любом изменении структуры.
- Не делай сервис-обёртку без логики. Если класс только вызывает репозиторий без валидации, маппинга, проверки прав или бизнес-правила, используй репозиторий внутри уже существующего сервиса.
- Breaking changes публичного API запрещены без явного подтверждения пользователя.

## Сервисы и публичный API классов

- Называй сервисы по операции, которую они выполняют, — глаголом: `CreateEmployee`, `GetEmployeeById`, `SearchEmployee`, `UpdateRole`. Безликие суффиксы вроде `Service`, `Manager`, `Helper` не используй.
- Один сервисный класс — одна операция: ровно одна публичная точка входа (например, `execute`) с параметрами или без.
- Все вспомогательные методы сервиса — приватные.
- Если в языке есть разметка асинхронности (`async`, `suspend` и т.п.), публичные методы, обращающиеся к хранилищу или к другим асинхронным методам, делай асинхронными. Не блокируй поток в асинхронном коде.
- Один файл — один публичный класс / тип верхнего уровня. Для дополнительного helper- или data-типа заводи отдельный файл с совпадающим названием (если язык не диктует иное).
- Не держи общие значения и функции в статических «свалках» внутри классов; выбирай enum, объявления верхнего уровня модуля или отдельные классы по смыслу.
- Для классов, которые можно изменить в коде проекта, не пиши внешние функции-расширения, monkey-patching и т.п. — добавляй методы в сам класс.
- Для цепочек из трёх и более вызовов переноси каждый вызов на отдельную строку.
- Для нетривиальных SQL-запросов в коде используй многострочный формат; параметры и ключевые части запроса размещай читаемо на отдельных строках.
- Не выводи диагностику в stdout (`println`, `print`, `console.log`, `fmt.Println` и т.п.); используй логгер проекта.
- Не бросай generic exceptions (`Exception`, `RuntimeException`, `Error`, голые строки и т.п.); используй специализированные исключения проекта.

## Именование

- Классы точек входа называются существительным (ресурсом) с принятым в проекте суффиксом (`*Endpoint`, `*Controller`, `*Api`, `*Handler`).
- Классы доступа к данным — с суффиксом `*Repository` или `*Adapter` (или принятым в проекте аналогом).
- Модели входящих запросов — с суффиксом `Request`, модели ответов — `Response`.
- Не вводи строковые константы без крайней необходимости; вместо наборов строковых значений используй enum (или ближайший аналог языка).
- Значения кодов и типов, хранимые в БД, пиши прописными буквами: `MANAGED_SYSTEM_ACCOUNT`, а не `managed_system_account`.

## Входящие данные

- Модели запросов должны игнорировать неизвестные поля, а не падать на них — так клиент и сервер можно обновлять независимо.
- Все данные, приходящие от клиента, считай необязательными (nullable / optional): и параметры обработчиков точки входа, и поля моделей запросов. Невалидные данные должны отсекаться на этапе валидации с понятной ошибкой, а не падать на несоответствии типов до неё.
- Коллекции значений в моделях запросов представляй множествами (`Set`), а не списками — это исключает дубли при обработке. Соответствующие поля ответа, отражающие такой набор, тоже делай множествами.
- Коллекции в сущностях делай обязательными с пустым значением по умолчанию; при конвертации необязательной коллекции из запроса в сущность подставляй пустую коллекцию.

## Валидация и ошибки

- Валидацию запросов выполняй в отдельных классах с префиксом `Validate*`: `ValidateCreateRoleRequest`, `ValidateUpdateRoleRequest` и т.п.
- Валидацию строй последовательной цепочкой проверок, которая останавливается на первой сработавшей проверке и бросает исключение валидации с собранными нарушениями. Используй готовый механизм проекта, а не ручные `if (errors.isNotEmpty()) throw ...` в каждом сервисе.
- В тексте нарушения для конкретного элемента коллекции указывай его идентификатор, чтобы ошибка была адресной: «Сотрудник c ID=42 не существует», а не безличное «Сотрудник не существует».
- Ключ нарушения (`key`, `field` и т.п.) должен соответствовать реальному полю запроса, к которому относится ошибка; не копируй его из соседней проверки.
- Используй специализированные исключения проекта по смыслу: некорректный запрос, сущность не найдена, ошибка валидации, нет прав, конфликт состояния.
- Для справочников отсутствие записи — ошибка ввода, а не «не найдено» (HTTP 404): возвращай ошибку валидации.
- Тексты ошибок отображаются пользователю. Не используй в них технические имена полей, camelCase, snake_case или JSON-ключи. Пиши на языке интерфейса продукта.
- Для строковых полей, идентифицирующих запись, проверяй пустые и состоящие из пробелов значения в create/upsert-логике и возвращай понятное сообщение.

## Авторизация

- Проверяй права через единый механизм авторизации проекта. Не разбрасывай по обработчикам точечные проверки (аннотации, декораторы, middleware «на месте»), если в проекте есть централизованный механизм.
