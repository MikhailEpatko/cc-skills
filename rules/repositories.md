## Работа с репозиториями

- Перед запросом данных по списку идентификаторов всегда проверяй список на пустоту. Для пустого списка сразу возвращай пустой результат и не вызывай репозиторий: `IN ()` — некорректный SQL, а часть драйверов и ORM обрабатывают его непредсказуемо.
- Методы репозиториев возвращают материализованный результат (сущность, коллекцию, страницу), а не ленивые или реактивные потоки (`Flux`, `Flow`, курсоры, генераторы), если стриминг не является явным требованием задачи.

### Запрет антипаттерна `orisnull`

- Не используй антипаттерн `orisnull` — обёртку опционального параметра вида `(:param is null or column = :param)`. Вместо него собирай SQL динамически: добавляй условие в запрос только тогда, когда параметр задан.
- Причина: драйверы кешируют prepared statements, и СУБД (например, PostgreSQL после нескольких выполнений) переходит на generic plan, где `:param is null` не сворачивается в константу. Индекс по колонке не применяется, и запрос вырождается в полный скан таблицы.
- Пример нарушения:

```sql
and (:resolveStatus is null or t.resolve_status = :resolveStatus)
```

- Правильный подход — динамическая сборка условий в адаптере: накапливай фрагменты `where` в списке, склеивай их и биндь только реально переданные параметры. Если в проекте уже есть эталонная реализация такого адаптера — следуй ей (укажи её в `CLAUDE.md`).
- Для keyset-пагинации вместо `(:lastId is null or id > :lastId)` передавай `lastId = 0`: условие `id > 0` эквивалентно отсутствию фильтра и всегда индексируемо.
- Для поиска по подстроке (`like` / `ilike '%...%'`) динамическая сборка обязательна: только тогда сможет примениться специализированный индекс (например, trigram-индекс `gin (name gin_trgm_ops)` в PostgreSQL).
- Исключение: `IS NULL` не является антипаттерном, когда несёт бизнес-семантику самих данных, а не «параметр не задан». Примеры: `(t.date_start is null or t.date_start <= now())`, `u.id is null or u.blocked = false` в LEFT JOIN, `channel_type is null` как «для всех каналов». Такие условия не переписывай.
