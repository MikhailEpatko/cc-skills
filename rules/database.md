# Изменение данных, аудит и миграции

Правила для проектов с реляционной БД. Конкретные имена таблиц аудита, колонок авторства и
идентификатор технического пользователя указывай в `CLAUDE.md` проекта.

## Изменение данных

- Пиши в таблицу только реально изменённые данные — не выполняй «пустых» апдейтов и удалений-вставок без фактических изменений. Особенно это важно, если ведётся аудит изменений: пустой апдейт порождает ложную запись в аудите.
- При обновлении сущности сохраняй её только если запрос действительно что-то поменял. Инкапсулируй это в методах сущности: «нужно ли обновление» (`needUpdate(request)`) и «применить обновление» (`update(authorId, request)`). Пример: `if (group.needUpdate(request)) repository.save(group.update(authorId, request))`.
- Задачу «привести состав таблицы в соответствие с запросом» решай через сравнение множеств, а не грубым «удалить всё + вставить заново». Прочитай существующие записи, вычисли `toAdd = запрос - существующие` и `toDelete = существующие - запрос`, добавь только `toAdd`, удали только `toDelete`.
- Перед пакетной вставкой / удалением проверяй, что коллекция непуста, чтобы не выполнять бессмысленные запросы.

## Аудит на триггерах БД

Действует, если аудит построен на триггерах, которые берут автора изменения (`modified_by` или аналог) из самой строки.

- Перед **любым** удалением строк из таблицы под аудитом проставляй им автора и время изменения (`modified_by = <автор>`, `modified_at = current_timestamp`) отдельным апдейтом, и только затем удаляй. Правило действует для всех удалений: одиночное удаление сущности, синхронизация состава таблицы, каскадная зачистка связанных таблиц, зачистка по фильтру.
- Причина: триггер записывает в аудит то значение автора, которое видит в строке в момент удаления. Без предварительного апдейта автором удаления окажется тот, кто менял строку в прошлый раз.
- Автором ставь пользователя, инициировавшего операцию. Для фоновых и планировщиковых сценариев, где нет запроса пользователя, используй технический аккаунт системы.
- При каскадном удалении апдейт нужен каждой таблице цепочки, а не только корневой.

## Миграции и SQL

- `TRUNCATE` в миграциях запрещён.
- Необязательные поля не делай nullable в БД, если они логически могут быть пустыми: массивы задавай как `NOT NULL DEFAULT '{}'`, текстовые поля как `NOT NULL DEFAULT ''`.
- Первичные ключи таблиц — суррогатный `bigint`, генерируемый БД (`bigint primary key generated always as identity` в PostgreSQL или аналог).
- Если инструмент миграций выполняет скрипт внутри транзакции (Liquibase, Flyway и т.п. по умолчанию), не используй операции, которые в транзакции невозможны (например, `CREATE INDEX CONCURRENTLY` в PostgreSQL). Используй обычный `create index if not exists`.

### Аудит в миграциях

- Если миграция меняет данные таблицы под триггером аудита, автор изменения должен быть проставлен явно, иначе в аудит попадёт автор предыдущего изменения.
- Перед `delete` отдельным `update` проставляй удаляемым строкам автора удаления:

```sql
update some_table
   set modified_at = current_timestamp,
       modified_by = '<id технического пользователя>'
 where parent_id in (...);

delete from some_table
 where parent_id in (...);
```

- В каждом `update`, меняющем данные, добавляй `modified_at = current_timestamp` и `modified_by = ...` к изменяемым полям — отдельного «догоняющего» апдейта не требуется.
- В `insert` заполняй все колонки авторства: `created_at`, `created_by`, `modified_at`, `modified_by`.
- В качестве автора используй технический аккаунт системы (его идентификатор — в `CLAUDE.md` проекта).
- Правило распространяется и на каскадные зачистки: каждой таблице цепочки нужен свой `update` перед её `delete`.
