# Стиль тестов

Общие правила, не зависящие от языка. Базовые тестовые конфигурации, фикстуры, эталонные тесты и
команды запуска проекта перечисляй в `CLAUDE.md` проекта.

## Общие принципы

- API-тесты и интеграционные тесты строй поверх общих базовых конфигураций проекта (тестовое окружение, моки внешних систем, общие фикстуры), а не поднимай своё окружение в каждом тесте.
- Используй одну библиотеку assert-ов, принятую в проекте; не смешивай разные стили проверок в одной кодовой базе.

## Архитектурные проверки

- Если проект проверяется архитектурными тестами (ArchUnit, import-linter, dependency-cruiser и т.п.), учитывай их: они контролируют слои, именование, запрещённые конструкции и правила тестового контекста.
- Если меняешь структуру API, сервисов, репозиториев или моделей запросов, ожидай влияние на эти тесты.

## Тяжёлый тестовый контекст

- Дорогой тестовый контекст (DI-контейнер, БД, миграции, HTTP-сервер) должен подниматься за прогон один раз. Каждый лишний контекст — это минуты прогона.
- Не используй в тестах механизмы, которые форкают или пересоздают общий контекст для отдельного тестового класса. Пример для Spring: `@TestPropertySource`, `@MockBean` / `@MockitoBean` / `@SpykBean` / `@MockkBean` и их множественные формы, `@DirtiesContext`, `@ActiveProfiles`, вложенные `@TestConfiguration` — всё это меняет ключ кеша контекста.
- Общие спаи и подмены бинов объявляй в одной общей тестовой конфигурации, подключённой ко всем тестам. Спай должен быть прозрачен — делегировать в реальную реализацию.
- Другое значение настройки задавай ручной сборкой тестируемого объекта поверх объектов общего контекста (копия объекта настроек с изменённым полем, явный аргумент конструктора), а не переопределением конфигурации контекста.
- Мок вместо спая (заглушку, которую нельзя включать глобально) делай локальным и передавай в собранный вручную объект.
- У собранного вручную объекта нет прокси контейнера, поэтому декларативные транзакции, кеширование и т.п. на нём не работают. Если тест проверяет откат, открывай транзакцию явно.
- Если объект обязан быть подменён именно в контексте, выноси делегирующую обёртку в общую тестовую конфигурацию, а не в локальную. Обёртка должна быть прозрачной по умолчанию, а включаемый сбой — одноразовым, чтобы упавший тест не ломал следующие.

## Fixtures и данные

- Для подготовки тестовых данных используй фикстуры и фабрики проекта.
- Не хардкодь ID. ID генерируются базой данных и должны браться из созданных fixture-объектов.
- Если тесту нужен идентификатор созданной сущности, бери его из сохранённой сущности.

## Именование тестов

- В имени теста (и в описании, если фреймворк его поддерживает: `@DisplayName`, `describe/it`, docstring) описывай действие и ожидаемый результат.
- Не указывай роль пользователя в имени теста.
- Тест называется по поведению системы, а не по внутренним деталям реализации.

## Request/response и API-проверки

- Для эндпоинтов проверяй ожидаемые HTTP-коды: успешный ответ, ошибки валидации, отсутствие доступа и отсутствие основной сущности, если применимо.
- Для справочников отсутствие записи проверяй как ошибку ввода, а не как 404.
- Сообщения ошибок в тестах должны соответствовать пользовательским текстам без технических имён полей.

## Репозитории и пустые списки

- Если код запрашивает данные по списку идентификаторов, тестируй сценарий пустого списка, когда это влияет на поведение.
- Проверяй, что для пустого списка код возвращает пустой результат и не зависит от некорректного SQL `IN ()`.

## Миграции

- Статические правила, проверяющие все скрипты миграций сразу (например, запрет `TRUNCATE`), допустимы.
- Тесты на отдельные скрипты миграций не пиши — см. «Антипаттерны тестов».

## Запуск проверок

- Перед завершением задачи запускай линтер / статический анализ, архитектурные тесты и тесты кода, затронутого задачей (см. раздел «Проверка задачи перед завершением» в `CLAUDE.md`). Тесты незатронутого кода не запускай. Полную проверку проекта — только по явной просьбе пользователя.
- Для точечной проверки используй фильтр тест-раннера по имени теста или маске пакета / модуля (`--tests`, `-k`, `-run`, `-t` и т.п.).
- Если линтер / форматтер запускается в режиме автоисправления и правит файлы вне текущей задачи, не откатывай эти изменения: следующий запуск проверок применит их снова.

## Что тестировать

- Валидацию входных данных и человекочитаемые ошибки.
- Проверки доступа и разрешений.
- Бизнес-логику сервисов через их публичную точку входа.
- Маппинг сущность / запрос / ответ, если в нём есть логика или риск регрессии.
- Интеграцию endpoint -> service -> repository для пользовательских сценариев.

## Что не тестировать напрямую

- Приватные методы; тестируй их через публичную точку входа.
- Простые pass-through вызовы без бизнес-логики.
- Код сторонних библиотек и инфраструктуру фреймворка без проектной логики.

## Антипаттерны тестов

- **Негативный тест проходит по чужой причине.** Валидация, останавливающаяся на первой сработавшей проверке, позволяет тесту «ошибка X», проверяющему только HTTP 400, зеленеть из-за ошибки Y. В негативном тесте проверяй ключ и текст нарушения, а входные данные собирай так, чтобы все проверки, кроме целевой, проходили.
- **Мок реализует проверяемое поведение.** Если результат, который assert-ит тест, вычислен внутри мока или заглушки, тест проверяет мок, а не код. Мокай только внешние границы (сервисы аутентификации, внешние API, коннекторы, время), а проверяемую логику прогоняй настоящую.
- **Ожидаемое значение вычислено тестируемым кодом.** Эталон, построенный тем же маппером, билдером или хелпером, что и результат, совпадёт с ним при любой ошибке. Ожидаемые значения задавай литералами или из fixture-данных.
- **Имя обещает больше, чем проверяет тест.** Имя «роль удаляется вместе со связями» при assert-е только кода 200 вводит в заблуждение. Либо добавь проверки обещанного, либо сузь имя до реально проверяемого.
- **Регрессионный тест, который ни разу не падал.** Тест на баг должен падать на коде до фикса по той причине, которую описывает баг, и проходить после фикса. Иначе он доказывает работу моков, а не исправление.
- **Тесты скриптов миграций.** Не проверяй результат применения конкретной миграции (данные, колонки, индексы после неё): миграция выполняется один раз, а тест остаётся навсегда и ломается при следующих изменениях схемы. Проверяй поведение приложения поверх новой схемы. Статические правила для всех миграций сразу — не антипаттерн.
- **Тесты сгенерированной API-документации.** Не проверяй сгенерированный документ OpenAPI / Swagger (схемы, коды ответов, обязательные поля, описания) и то, как генератор документации увидит модель (геттеры, аннотации и декораторы документации). Документация — не поведение приложения: такие тесты ломаются при обновлении генератора и правке описаний, не ловя регрессий API. Проверяй реальные запросы и ответы эндпоинта. Архитектурные правила над аннотациями документации — не антипаттерн.
- **Тесты одного API, отличающиеся только набором проверяемых полей.** Если несколько тестов делают один и тот же запрос с одинаковыми данными и различаются лишь тем, какие поля ответа assert-ят, объедини их в один тест с полной проверкой ответа. Отдельный тест нужен только для отдельного сценария: другие входные данные, права, состояние БД.
