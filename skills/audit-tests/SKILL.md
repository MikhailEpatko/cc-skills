# Аудит тестов

Область аудита: $ARGUMENTS. Если область не указана — спроси её у пользователя и ничего не начинай.

Цель — уверенность в тестах, а не число удалённых строк. Лучше три доказанных кандидата, чем
тридцать спорных.

## Железное правило

```
НИКАКИХ ИЗМЕНЕНИЙ В ТЕСТАХ ИЛИ КОДЕ БЕЗ ЯВНОГО ПОДТВЕРЖДЕНИЯ ПОЛЬЗОВАТЕЛЯ
```

- Удаление, объединение, переименование, правка assert-ов, fixtures, хелперов и продового кода —
  всё это изменения.
- Подтверждение действует только на перечисленные пользователем номера кандидатов и только в
  том виде, в каком кандидат был описан. Любой шаг сверх описанного (правка соседнего теста,
  fixture, продового кода) — новый вопрос пользователю.
- Молчание, «ок, смотри дальше», одобрение отчёта в целом — не подтверждение изменений.

## Защищённые тесты

Не являются кандидатами, не меняются и не удаляются даже по косвенным причинам (переименование,
перенос хелпера, «заодно поправил»):

- архитектурные тесты и их хелперы (ArchUnit, import-linter, dependency-cruiser, deptrac и
  аналоги) — правила слоёв, именования, запрещённых конструкций, тестового контекста;
- статические правила, проверяющие все скрипты миграций сразу;
- тесты, перечисленные как защищённые в `CLAUDE.md` проекта.

Если защищённый тест кажется неверным — опиши это в отчёте отдельным замечанием без предложения
удаления.

## Процесс

1. **Прочитай правила.** Правила тестов проекта (`test-style.md` в `.claude/rules/` или
   `~/.claude/rules/`) и `CLAUDE.md`, особенно раздел «Антипаттерны тестов» — это основной список
   признаков кандидатов.
2. **Поиск (только чтение).** По каждому тесту из области прочитай целиком сам тест, продовый код,
   который он проверяет, и соседние тесты того же API или сервиса. Структуру БД сверяй через
   инструмент доступа к БД из `CLAUDE.md`, а не по догадке.
3. **Кандидаты.** Кроме антипаттернов из правил, ищи:
   - тесты без содержательных assert-ов;
   - дубли: тот же сценарий с теми же данными проверен в другом тесте не слабее;
   - тесты приватной логики, уже покрытой через публичную точку входа сервиса или эндпоинт;
   - тесты, которые сломаются при рефакторинге без изменения поведения;
   - тесты сгенерированной API-документации: запросы к эндпоинту документа OpenAPI / Swagger,
     проверки схем, кодов ответов и описаний в документе, проверки видимости полей для
     генератора документации (геттеры, аннотации / декораторы документации). Покрытие для них не
     требуется — документация не поведение; в поле «какой тест покрывает» укажи «не требуется:
     тест API-документации». Архитектурные правила над аннотациями документации — защищённые.
4. **Доказательства.** Для каждого кандидата заполни все поля. Пустое поле — кандидат не готов,
   в список на изменение его не включай:
   - тест: файл, класс / группа, метод / функция, отображаемое имя;
   - какую регрессию он реально ловит;
   - какой антипаттерн и почему;
   - какой другой тест покрывает то же поведение (путь и метод) или почему покрытие не нужно;
   - предлагаемое действие: удалить / объединить с … / переписать проверку …;
   - риск и команда точечной проверки.
5. **Отчёт и вопрос.** Выведи пронумерованную таблицу кандидатов и спроси, какие номера
   применить. Если аудит идёт в рамках задачи — сохрани отчёт в `ai/<TASK-ID>/test-audit.md`.
6. **Применение.** Только подтверждённые номера. Затем выполни проверки из раздела «Проверка
   задачи перед завершением» в `CLAUDE.md`: линтер и тесты области аудита плюс тесты, в которые
   перенесены проверки при объединении (и архитектурные тесты, если они запускаются отдельно).
   Сообщи итог с фактическим выводом команд.

## Не является причиной удаления

| Довод | Реальность |
|-------|------------|
| «Тест медленный» | Медленный — повод ускорить, а не удалить |
| «Тест похож на реализацию» | Может быть единственной проверкой контракта. Докажи обратное |
| «Этот API покрыт и так» | Назови конкретный тест и сценарий, иначе не покрыт |
| «Тест падает» | Возможно, это баг в продовом коде. Воспроизведи и доложи |
| «Мелочь, поправлю без вопроса» | Любая правка — только после подтверждения |

## Красные флаги — остановись

- Правишь файл, а пользователь ещё не назвал номера кандидатов.
- Трогаешь защищённый тест.
- В строке кандидата нет ссылки на тест, который покрывает то же поведение.
- Добавляешь в список сомнительного кандидата, «чтобы список был полнее».
